# agent-sever

HTTP-сервис `agentd`: принимает промпт по HTTP, прогоняет его через явный
конвейер обработки (нормализация → входные политики → вызов модели →
выходные политики → судья) и возвращает нормализованный ответ. Ключ
провайдера принадлежит сервису и никогда не приходит от клиента.

Ядро (вызов модели, настройки диалога, телеметрия, конвейер) живёт в
библиотеке `agentcore` из репозитория
[agent-cli](https://github.com/Egor-Liadsky/agent-cli) и подключается
git-зависимостью. Оттуда же подключается `agentupstream` — крейт с обращением
к облачному провайдеру. Он вынесен из ядра намеренно: консольный клиент
`agentcli` от него не зависит, поэтому ходить в облако напрямую он не может, а
делает это только через `POST /v1/chat` этого сервиса. Локальный Ollama —
исключение: клиент вызывает его сам, минуя сервис.

Провайдера выбирает сам сервис по полю `settings.provider` запроса:
`cloud` — `agentupstream`, `ollama` — локальный агент из `agentcore`.

## Конфигурация

Конфигурация читается только из переменных окружения. Пользовательский
конфиг консольного клиента (`~/.config/agentcli/config.toml`) сервис
не читает.

Перед чтением окружения сервис подхватывает `.env` из текущей рабочей
директории через `dotenvy` (файл необязателен, отсутствие не ошибка).
Это удобно для локального запуска; в проде переменные должны приходить
из окружения контейнера/оркестратора — `.env` для этого не нужен и в
образ не копируется.

| Переменная                   | По умолчанию              | Назначение |
|------------------------------|---------------------------|------------|
| `AGENTD_UPSTREAM_API_KEY`    | —, обязательна            | Ключ провайдера модели. Без него сервис не стартует |
| `AGENTD_LISTEN_ADDR`         | `0.0.0.0:8080`            | Адрес прослушивания целиком |
| `PORT`                       | —                         | Порт, если `AGENTD_LISTEN_ADDR` не задан (хостинги задают его сами) |
| `AGENTD_UPSTREAM_BASE_URL`   | `https://api.deepseek.com`| Базовый адрес OpenAI-совместимого API |
| `AGENTD_MODEL`               | `deepseek-chat`           | Модель по умолчанию |
| `AGENTD_ALLOWED_MODELS`      | пусто                     | Список моделей через запятую. Пусто — разрешена только `AGENTD_MODEL` |
| `AGENTD_OLLAMA_URL`          | —                         | Адрес локального Ollama. Не задан — `provider: "ollama"` в запросе отклоняется |
| `AGENTD_CLIENT_TOKENS`       | пусто                     | Клиентские токены через запятую. Пусто — аутентификация выключена |
| `AGENTD_REQUEST_TIMEOUT_SECS`| `60`                      | Таймаут запроса к провайдеру |
| `AGENTD_MAX_BODY_BYTES`      | `262144`                  | Предельный размер тела запроса |
| `AGENTD_MAX_CONCURRENCY`     | `16`                      | Предел одновременно обрабатываемых запросов |
| `AGENTD_LOG_FORMAT`          | `json`                    | Формат журнала: `json` или `text` |
| `AGENTD_LOG_TARGET`          | `stdout`                  | Куда писать журнал: `stdout` или `stderr` |
| `AGENTD_LOG_CONTENT`         | `false`                   | Писать ли в журнал тексты промптов и ответов |
| `AGENTD_DB_PATH`             | `agentd.db`               | Путь к файлу базы SQLite. Каталог создаётся при старте, если его нет |
| `AGENTD_DB_MAX_CONNECTIONS`  | `5`                       | Размер пула соединений с базой. `0` или нечисловое значение — ошибка старта |
| `AGENTD_DB_BUSY_TIMEOUT_MS`  | `5000`                    | Ожидание освобождения блокировки записи. `0` или нечисловое значение — ошибка старта |
| `AGENTD_MAX_CONTEXT_TOKENS`  | —                         | Лимит контекстного окна по умолчанию, в токенах. Не задан — размер истории не проверяется. `0` или нечисловое значение — ошибка старта |
| `AGENTD_SUMMARY_ENABLED`     | `false`                   | Компактизация истории включена по умолчанию для новых запросов чата. Чат может включить или выключить её своим значением |
| `AGENTD_SUMMARY_KEEP_MESSAGES` | `20`                    | Потолок дословного хвоста компактизации, в сообщениях. Клиент может только сузить. `0` или нечисловое значение — ошибка старта |
| `AGENTD_SUMMARY_STEP_MESSAGES` | `10`                    | Нижняя граница шага пересказа, в сообщениях. Клиент может только увеличить. `0` или нечисловое значение — ошибка старта |
| `AGENTD_SUMMARY_MAX_CHARS`   | `4000`                    | Верхняя граница длины пересказа, в символах. `0` или нечисловое значение — ошибка старта |
| `AGENTD_SUMMARY_MODEL`       | —                         | Модель для построения пересказа. Не задана — используется модель чата |

> **Предупреждение.** Пустой `AGENTD_CLIENT_TOKENS` означает, что сервис
> обслуживает любого, кто до него дотянулся: проверка токена выключена.
> Сервис говорит об этом отдельной записью `WARN` при старте. В открытую
> сеть такой сервис выставлять нельзя.

Ключ провайдера в журнале появляется только маскированным
(`secr***alue`), целиком он не пишется никогда.

> **Требование к клиентским токенам.** Владелец чата в базе хранится как
> `sha256("agentd-client-token:v1:" || токен)`, а не сам токен. Это не
> хранилище паролей: токен с малой энтропией подбирается по отпечатку
> перебором. `AGENTD_CLIENT_TOKENS` должны быть случайными строками
> достаточной длины.

> **Приватность базы.** Файл `AGENTD_DB_PATH` (и его WAL-спутники `-wal`,
> `-shm`) содержит переписку в открытом виде — шифрование вне области
> сервиса. За защиту файла отвечает владелец базы: права доступа только
> для процесса сервиса. Удаление чата (`DELETE /v1/chats/{id}`) — способ
> удалить его переписку из хранилища.

## Запуск

```bash
AGENTD_UPSTREAM_API_KEY=sk-... \
AGENTD_MODEL=deepseek-chat \
PORT=8080 \
cargo run --release
```

Пример запроса:

```bash
curl -sS -X POST http://127.0.0.1:8080/v1/chat \
  -H 'content-type: application/json' \
  -d '{"prompt": "Привет!", "settings": {"temperature": 0.3}}'
```

Успешный ответ:

```json
{
  "request_id": "0f0f…",
  "content": "Привет! Чем помочь?",
  "reasoning": null,
  "model": "deepseek-chat",
  "usage": { "prompt_tokens": 11, "completion_tokens": 7, "total_tokens": 18, "reasoning_tokens": null },
  "timing": { "duration_ms": 812, "sent_at": 1788976567, "received_at": 1788976568 },
  "policy": { "input": [], "output": [], "judge": null }
}
```

При включённой аутентификации к запросу добавляется заголовок
`Authorization: Bearer <токен>`.

## Эндпоинты

| Метод и путь            | Назначение |
|--------------------------|------------|
| `POST /v1/chat`          | Диалог с моделью. Ровно одно из полей `prompt` или `messages`; с полем `chat_id` — только `prompt`, история берётся из чата |
| `POST /v1/chats`         | Создание чата |
| `GET /v1/chats`          | Список чатов клиента, постранично (`limit`, `cursor`) |
| `GET /v1/chats/{id}`     | Чат вместе со страницей его сообщений (`limit`, `after`) |
| `PATCH /v1/chats/{id}`   | Переименование чата и/или постоянное изменение его настроек |
| `DELETE /v1/chats/{id}`  | Удаление чата вместе с сообщениями |
| `POST /v1/chats/{id}/messages` | Дозапись готовых сообщений в чат без обращения к провайдеру |
| `GET /v1/models`         | Модели, разрешённые конфигурацией |
| `GET /healthz`           | Живость процесса, к провайдеру и базе не обращается |
| `GET /readyz`            | Готовность: 200 при валидной конфигурации и рабочей базе, 503 иначе |

Чат принадлежит клиенту, который его создал (владение определяется
отпечатком `AGENTD_CLIENT_TOKENS`, см. предупреждение выше). Обращение к
чужому или несуществующему чату отвечает одинаково — `404
chat_not_found`.

### Диалог в существующем чате

```bash
curl -sS -X POST http://127.0.0.1:8080/v1/chats \
  -H 'content-type: application/json' -d '{}'
# => { "id": "…", "title": "Новый чат", "settings": {…}, "message_count": 0, … }

curl -sS -X POST http://127.0.0.1:8080/v1/chat \
  -H 'content-type: application/json' \
  -d '{"chat_id": "<id из ответа выше>", "prompt": "Привет!"}'
# => { …, "chat_id": "<id>", "seq": 2 }
```

Без `chat_id` `POST /v1/chat` ведёт себя как раньше: история — только из
тела запроса, в базу ничего не пишется, `chat_id` в ответе — `null`.
Поле `settings` при заданном `chat_id` переопределяет настройки чата
только на этот запрос; чтобы изменить их насовсем, используется
`PATCH /v1/chats/{id}`.

### Лимит контекстного окна

`AGENTD_MAX_CONTEXT_TOKENS` задаёт операторский лимит контекстного окна по
умолчанию, в токенах. Не задан — операторского лимита нет, но клиентский
лимит (ниже) при этом продолжает действовать сам по себе: отсутствие
операторского значения — не повод отказывать в проверке. `settings` в
`PATCH /v1/chats/{id}` принимает необязательное поле `max_context_tokens`
и сохраняет его в настройках чата наравне с `model`, `reasoning` и
параметрами сэмплирования: число задаёт лимит, `null` снимает его,
отсутствие поля оставляет сохранённое значение прежним. Сохранённый лимит
действует как значение по умолчанию для каждого `POST /v1/chat` этого чата.
`settings.max_context_tokens` в `POST /v1/chat` остаётся разовым
переопределением поверх сохранённого лимита чата — действует только на этот
вызов и не сохраняется, даже когда запрос ссылается на `chat_id`.

Эффективный лимит запроса — минимум из заданных значений: заданы оба —
действует клиентское (оно не может превышать операторское), задан только
один — действует он, не задан ни один — лимит не проверяется. Клиентское
значение шире операторского отклоняется `400 context_limit_invalid` — как в
`POST /v1/chat`, так и при сохранении в `POST /v1/chats` и
`PATCH /v1/chats/{id}` (проверка при сохранении применяется независимо от
провайдера чата, включая `ollama`: лимит относится к размеру истории, а не
к способу вызова модели). Перед вызовом модели сервис оценивает размер
истории, которая фактически уйдёт провайдеру (с учётом компактизации ниже),
в токенах — приближённо, по длине текста (`ceil(символы / 4)`), точного
токенизатора провайдера у сервиса нет. Превышение эффективного лимита
отклоняется `400 context_limit_exceeded` без обращения к провайдеру и без
записи в историю чата.

### Компактизация истории

Чтобы длинный чат не упирался в лимит контекста, сервис умеет заменять
вытесненную часть истории кратким пересказом. Последние `N` сохранённых
сообщений (`summary_keep_messages`, потолок — `AGENTD_SUMMARY_KEEP_MESSAGES`)
уходят провайдеру дословно вместе с новым сообщением; всё, что старше,
заменяется одним текстом-пересказом, помещаемым в начало истории. Граница
хвоста при необходимости сдвигается на ближайшее сообщение роли `user`,
чтобы хвост не начинался с ответа ассистента без вопроса — поэтому `N` это
верхняя граница размера хвоста, а не точное число. Сообщения в хранилище не
удаляются и не изменяются: `GET /v1/chats/{id}/messages` всегда отдаёт
полную переписку.

Пересказ обновляется ступенчато: новый строится, когда за границей хвоста
накопилось не меньше `summary_step_messages` (нижняя граница —
`AGENTD_SUMMARY_STEP_MESSAGES`) ещё не пересказанных сообщений; до этого
подставляется прежний пересказ без обращения к модели. Построение —
ленивое, при сборке истории очередного `POST /v1/chat`, до проверки лимита
контекста: так компактизация может спасти запрос от
`context_limit_exceeded`. Модель для пересказа берётся из
`AGENTD_SUMMARY_MODEL` (не задана — используется модель чата), рассуждение и
`thinking` для этого вызова выключены, а результат обрезается до
`AGENTD_SUMMARY_MAX_CHARS` символов. Ошибка вызова модели ради пересказа не
роняет пользовательский запрос: сервис пишет `WARN`, использует прежний
пересказ (или полную историю, если пересказа ещё нет) и продолжает как
обычно — в том числе проверяет лимит контекста по фактически отправляемой
истории.

Компактизация выключена по умолчанию (`AGENTD_SUMMARY_ENABLED=false`); чат
может включить её своим значением `settings.summary_enabled` даже на
сервисе с выключенным умолчанием, и наоборот. Поля `settings.summary_enabled`,
`settings.summary_keep_messages` и `settings.summary_step_messages`
сохраняются в `POST /v1/chats` и `PATCH /v1/chats/{id}` той же семантикой
присутствия поля, что и `max_context_tokens` (отсутствие поля — прежнее
значение, `null` — возврат к операторскому умолчанию, число/булево —
задаёт), а в `POST /v1/chat` действуют разовым переопределением, не
сохраняясь. Клиентские `summary_keep_messages` и `summary_step_messages`
ограничены операторскими границами в обе стороны (сузить хвост, разредить
шаг) и нулём; нарушение отклоняется `400 summary_settings_invalid`. Модель
пересказа — операторский выбор и клиенту не передаётся.

`POST /v1/chat` без `chat_id` компактизации не подлежит: истории в
хранилище у него нет.

Ответ `POST /v1/chat` (с `chat_id`) содержит блок `context`:

```json
"context": { "replaced_messages": 6, "summary_built": true }
```

`replaced_messages` — сколько сохранённых сообщений заменено пересказом в
этом запросе (`0`, если компактизация не применялась), `summary_built` —
строился ли новый пересказ на этом запросе. `GET /v1/chats` и
`GET /v1/chats/{id}` возвращают пересказ полями только для чтения `summary`
(текст или `null`) и `summary_through_seq` (номер последнего пересказанного
сообщения или `null`); попытка прислать их в `POST /v1/chats` или
`PATCH /v1/chats/{id}` отклоняется `400` как неизвестное поле.

### Настройки чата

`settings` в `POST /v1/chats` и `PATCH /v1/chats/{id}` накладывается на
текущие настройки чата: отсутствующее поле остаётся прежним. Явный `null`
у параметра сэмплирования (`temperature`, `top_p`, `top_k`,
`frequency_penalty`, `presence_penalty`) снимает его, а поле
`custom_response_mode` включает и выключает кастомный формат ответа —
переданный `response_format` включает его сам.

### Чаты с локальным провайдером

Чат с настройками `provider: "ollama"` сервис хранит, но не обслуживает:
ответ в нём даёт Ollama на машине пользователя, а обмен попадает в базу
дозаписью (ниже). Поэтому для таких чатов не проверяются ни белый список
`AGENTD_ALLOWED_MODELS`, ни наличие `AGENTD_OLLAMA_URL` — их модель
принадлежит клиенту. Диалог через сервис (`POST /v1/chat` с `chat_id`
такого чата) по-прежнему требует настроенного `AGENTD_OLLAMA_URL` и без
него отвечает `400`.

### Дозапись готовых сообщений

Когда ответ получен не сервисом, а самим клиентом — так работает локальная
модель Ollama на машине пользователя, — обмен записывается в чат отдельным
запросом. Провайдер при этом не вызывается, стадии конвейера к тексту не
применяются, а весь список пишется одной транзакцией: либо все сообщения
появляются в чате, либо ни одно.

```bash
curl -sS -X POST http://127.0.0.1:8080/v1/chats/<id>/messages \
  -H 'content-type: application/json' -d '{
    "messages": [
      { "role": "user", "content": "Привет!" },
      { "role": "assistant", "content": "Здравствуйте!", "reasoning": null,
        "model": "llama3",
        "usage": { "prompt_tokens": 11, "completion_tokens": 7, "total_tokens": 18 },
        "timing": { "duration_ms": 120, "sent_at": 1000, "received_at": 1001 } }
    ]
  }'
# => 201 { "request_id": "…", "chat_id": "<id>", "seqs": [1, 2] }
```

Поля `reasoning`, `model`, `usage` и `timing` необязательны и учитываются
только у роли `assistant`. За один запрос принимается не больше 100
сообщений; пустой список, пустой текст сообщения, неизвестная роль и поле
`api_key` на любом уровне вложенности отклоняются как `400`. В журнал
попадают идентификатор чата и число сообщений, а их текст — только при
`AGENTD_LOG_CONTENT=true`.

Ошибки приходят единым конвертом:

```json
{ "error": { "code": "invalid_request", "message": "…", "request_id": "…" } }
```

| Код | Когда |
|-----|-------|
| 400 | Невалидный запрос: оба или ни одного из `prompt`/`messages`, поле `api_key`, модель вне белого списка, `ollama` без настроенного адреса, `messages` вместе с `chat_id`, пустое тело `PATCH`, `limit` вне диапазона, неизвестный курсор, неизвестное поле в `settings` (включая попытку записать `summary`/`summary_through_seq`), `max_context_tokens` больше операторского лимита — при вызове и при сохранении (`context_limit_invalid`), история больше эффективного лимита контекстного окна (`context_limit_exceeded`), `summary_keep_messages`/`summary_step_messages` вне операторских границ или ноль (`summary_settings_invalid`) |
| 401 | Нет клиентского токена или он неизвестен |
| 404 | Чат не существует, недоступен клиенту или идентификатор неверного вида (`chat_not_found`) |
| 413 | Тело больше `AGENTD_MAX_BODY_BYTES` |
| 422 | Запрос отклонён политикой конвейера |
| 429 | Превышена конкурентность либо провайдер ограничил частоту |
| 500 | Хранилище отказало (`storage_error`); клиенту уходит общее сообщение, подробности — только в журнал |
| 502 | Провайдер вернул ошибку |
| 504 | Провайдер не ответил в отведённое время |

Идентификатор запроса возвращается в заголовке `x-request-id` и в теле —
и в успешном ответе, и в ошибке.

## Контейнер

```bash
docker build -t agentd .
docker run --rm -p 8080:8080 \
  -v agentd-data:/var/lib/agentd \
  -e AGENTD_UPSTREAM_API_KEY=sk-... \
  agentd
```

Образ многостадийный: рантайм на `debian:bookworm-slim` без инструментов
сборки, порт берётся из `PORT`, `HEALTHCHECK` опрашивает `/healthz`.

Файл базы живёт в томе `/var/lib/agentd` (`ENV AGENTD_DB_PATH` в образе
указывает туда), а не в слое образа: без тома `-v` база и вся переписка
исчезали бы вместе с пересозданным контейнером. Каталог тома создаётся в
образе с владельцем `agentd` — тем же пользователем, под которым работает
процесс.

## Разработка против неопубликованного ядра

Образ и CI собираются из `main` репозитория `agent-cli`. Чтобы работать
против локальной копии ядра, положите рядом `.cargo/config.toml`
(он в `.gitignore`):

```toml
[patch."https://github.com/Egor-Liadsky/agent-cli"]
agentcore = { path = "../agent-cli/crates/core" }
agentupstream = { path = "../agent-cli/crates/upstream" }
```

Подменять нужно оба крейта: они лежат в одном репозитории, и половинчатый
`[patch]` собрал бы сервис из разных версий ядра.

Порядок обновления зависимостей `agentcore` и `agentupstream`:

1. Изменить ядро в `agent-cli`, прогнать там `cargo test`.
2. Запушить `agent-cli/main` — образ собирается именно из этой ветки.
3. В `agent-sever` временно убрать `[patch]` и выполнить
   `cargo generate-lockfile`, чтобы `Cargo.lock` зафиксировал новый коммит.
4. Прогнать `cargo test --locked` без `[patch]`: так расхождение ядра
   и сервиса обнаруживается до сборки образа.

Локальная сборка под `[patch]` переписывает записи `agentcore` и
`agentupstream` в
`Cargo.lock` на путь к соседнему каталогу. Образ собирается с `--locked`,
поэтому перед коммитом лок-файл нужно перегенерировать без `[patch]` —
шаг 3 выше. Проверить, что в лок-файле именно коммит, а не путь (и что у
обоих крейтов он один и тот же):

```bash
grep -A2 'name = "agentcore"' Cargo.lock
grep -A2 'name = "agentupstream"' Cargo.lock
```
