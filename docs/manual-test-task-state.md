# Ручной прогон автомата состояния задачи

Автотесты на `wiremock` проверяют механику автомата, но не проверяют, что
модель вообще отдаёт нужные предложения на живых текстах. Именно этот
разрыв пропустил застревание задачи на этапе `clarification`, поэтому
проверка против живого провайдера повторяется по записанному сценарию, а
не собирается заново каждый раз.

## Подготовка

```bash
cd agent-sever
set -a && . ./.env && set +a
export AGENTD_DB_PATH=/tmp/task-state-manual.db PORT=8099 \
       AGENTD_LOG_CONTENT=true AGENTD_TASK_STATE_ENABLED=true \
       AGENTD_TASK_STATE_AUTO_ENABLED=true AGENTD_CLIENT_TOKENS=testtoken
cargo run --release
```

Чат заводится `POST /v1/chats`, реплики уходят `POST /v1/chat` с
`chat_id`, состояние читается `GET /v1/chats/{id}/task`. Между обменом и
чтением состояния нужна пауза 20-30 секунд: трекер фоновый. Счётчики
`task_tracker_*` в блоке `context` ответа относятся к ПРЕДЫДУЩЕМУ
обмену — сверяться с ними, а не с текущим.

## Сценарий А. Автотрекер ведёт задачу от плана до проверки

Реплики подаются по одной, после каждой читается
`GET /v1/chats/{id}/task`.

1. «Хочу написать парсер CSV на Rust. Помоги спланировать работу.»
   Ожидается: этап `clarification`, шаг и ожидаемое действие описывают
   заданные вопросы, в журнале переходов запись `planning →
   clarification` с источником `auto`.
2. «План подходит. Задай уточняющие вопросы, если они есть.»
   Ожидается: этап остаётся `clarification`, но шаг и ожидаемое действие
   ОБНОВИЛИСЬ под новые вопросы; счётчик `task_tracker_updated` вырос,
   счётчик `task_tracker_rejected` — нет.
3. «Отвечаю: файлы до 100 МБ, разделитель запятая, кавычки по RFC 4180.
   Всё понятно, начинай выполнение.»
   Ожидается: этап `execution`, переход `clarification → execution`
   источником `auto`. Это ключевая проверка: подтверждение живёт в
   реплике пользователя, а не в ответе модели.
4. «Код готов, проверь его.»
   Ожидается: этап `validation`, переход `execution → validation`.
5. «Всё верно, задача закрыта.»
   Ожидается: этап остаётся `validation` — трекер не завершает задачу; в
   журнале не должно появиться перехода в `done` с источником `auto`.

Этап `execution`, удержанный на обмене 4, сам по себе дефектом не
является: если модель в этом обмене всё ещё правит собственный код
(например, чинит ошибки компиляции), `execution` — верное решение, и это
видно по обновившемуся шагу. Дефект — когда этап стоит при явном
подтверждении пользователя, а шаг и ожидаемое действие не меняются.

Признаки неисправности: этап не меняется два обмена подряд при явном
подтверждении; в журнале сервиса `reject_reason="invalid_edge"` на
предложении, совпадающем с текущим этапом; шаг и ожидаемое действие
буквально совпадают со значениями предыдущего обмена; строка «Ожидаемое
действие: …» в системном сообщении описывает то, что пользователь уже
сделал.

## Сценарий Б. Ручные переходы по HTTP

На свежем чате, без обращения к модели:

1. `{"stage":"execution"}` с `planning` → `400`, «переход не входит в
   допустимые рёбра автомата».
2. `{"stage":"mystery"}` → `400`, «неизвестный этап задачи».
3. `{"stage":"clarification","step":"шаг","expected_action":"действие"}`
   → `200`, этап `clarification`, журнал пополнился записью с источником
   `manual`.
4. `{"step":"другой шаг"}` (без `stage`) → `200`, этап не изменился,
   шаг обновлён, новой записи в журнале переходов НЕТ.
5. `{"stage":"done"}` с `clarification` → `400`, задача не завершена,
   `active_task_id` чата не изменился.
6. `POST .../task/pause` → `200`, в ответе `paused: true` и непустой
   бриф возобновления; затем любой переход, обновление шага и
   `{"stage":"done"}` → `400` с причиной про паузу.
7. `POST .../task/resume` → `200`, этап, шаг и ожидаемое действие те же,
   что до паузы.
8. Провести задачу до `validation` и отправить `{"stage":"done"}` →
   `200`, в ответе `new_task_id`, рабочая память задачи очищена, новая
   активная задача на `planning`.

## Сценарий В. TUI `agent-cli`

При запущенном сервисе: `cargo run -p agentcli -- chat`, `Ctrl+T` на
чате из сценария А.

1. На этапе `planning` список `←`/`→` должен предлагать
   `clarification`.
2. На этапе `clarification` список должен предлагать `execution` и
   `planning`.
3. `s` и `a` правят шаг и ожидаемое действие; `p`/`r` — пауза и снятие с
   паузы; после паузы экран показывает отметку и бриф.
4. Перечень «Последние переходы» должен показывать источники `manual` и
   `auto` вперемешку — так видно, что ручной и автоматический пути
   работают по одному автомату.
