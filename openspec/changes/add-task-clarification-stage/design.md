## Context

Текущий автомат в `src/task.rs` (`TaskStage`, `EDGES`, `can_transition`)
знает четыре этапа: `planning`, `execution`, `validation`, `done`, с
рёбрами `planning→execution`, `execution→validation`,
`validation→done`, `validation→execution`, `execution→planning`. Этап
хранится в БД как свободный `TEXT` (см. `src/store.rs`), поэтому
добавление нового значения не требует миграции схемы — только
расширения самого перечисления и списка рёбер в коде. Раздел системного
сообщения (`system_message_section`) и бриф возобновления
(`build_resume_brief`) интерполируют `task.stage` как обычную строку, не
завязываясь на конкретный набор этапов, поэтому тоже не требуют
доработки под новое значение. См. `proposal.md` — Why/What Changes.

## Goals / Non-Goals

**Goals:**
- Ввести этап `clarification` как обязательный шаг между `planning` и
  `execution`, чтобы автомат отражал: план собран → пользователю заданы
  уточняющие вопросы → пользователь подтвердил готовность → выполнение.
- Обучить промпт автотрекера предлагать переход в `clarification` и из
  неё в `execution` по тем же правилам, что и остальные предложения.

**Non-Goals:**
- Не меняется цикл `execution ⇄ validation` и переход в `done` — они уже
  реализованы и не требуют изменений (подтверждено пользователем при
  сборе плана).
- Не меняется хранилище (`store.rs`): `stage` остаётся свободным `TEXT`,
  миграция не нужна.
- Клиентская часть `agent-cli` (TUI-экран состояния задачи, список
  этапов в `crates/client`) в это изменение не входит — она правится
  отдельным изменением после того, как протокол `agentd` зафиксирует
  новый этап.

## Decisions

### Решение 1: прямое ребро `planning → execution` убирается
Чтобы уточнение плана было обязательным, а не опциональным шагом,
ребро `planning → execution` удаляется из `EDGES`, остаётся только
`planning → clarification → execution`. Альтернатива — оставить старое
ребро как "быстрый путь" для тривиальных задач — отклонена: пользователь
явно попросил отдельный обязательный этап анкетирования, а не
опциональный.

### Решение 2: `clarification → planning` как путь пересборки плана
Если в ходе вопросов выясняется, что план нужно менять, автомат
возвращает задачу в `planning` тем же путём, что уже работает для
`execution → planning`. Отдельного этапа "план пересобирается" не
вводится — `planning` уже покрывает эту работу.

### Решение 3: критерий перехода `clarification → execution` — только явное подтверждение пользователя
Трекер получает на вход последний ответ модели пользователю (как и для
всех прочих предложений — см. `tracker_prompt`). Явного сигнала "пользователь
подтвердил" в системе нет и не вводится: вместо этого промпт трекера
прямо указывает, что переход в `execution` из `clarification`
предлагается, только если ответ модели показывает, что пользователь
подтвердил готовность (например, ответил "да, начинай" на вопрос
модели). Это тот же приём, что и вся остальная логика трекера —
классификация последнего обмена, а не отдельный канал сигналов.
Альтернатива — вводить отдельное поле "user_confirmed" в DTO чата —
отклонена как избыточное усложнение протокола ради того, что уже
выражается текстом ответа.

### Решение 4: `parse`/`as_str` остаются исчерпывающим `match`
`TaskStage::parse` и `as_str` — обычные `match` без `_ =>`; добавление
варианта `Clarification` заставляет компилятор указать на все места,
которые нужно обновить (проверено: `system_message_section` и
`build_resume_brief` работают со строкой `task.stage` напрямую и правок
не требуют).

## Risks / Trade-offs

- [Риск] Удаление ребра `planning → execution` — breaking change для
  любых уже приостановленных задач или внешних клиентов, ожидающих
  старое поведение автомата → Митигация: `stage` в БД не проверяется
  внешним ключом/enum, старые записи с этапом `execution` продолжают
  работать как есть; ломается только *новый* переход из `planning`
  напрямую в `execution` — то, что и требуется по этому изменению.
- [Риск] Трекер может неверно классифицировать обычный уточняющий
  вопрос модели как готовность к `clarification`, либо не распознать
  явное согласие пользователя и застрять на `clarification` →
  Митигация: как и раньше, отклонённое трекером предложение не меняет
  состояние, ручной переход (`apply_manual_transition`) остаётся
  доступным как обходной путь.

## Migration Plan

Изменение только в коде сервиса `agentd`, миграция БД не нужна (этап —
свободный текст). Деплой — обычный релиз сервиса. Откат — предыдущая
версия бинарника продолжает читать записи с этапом `clarification` как
неизвестный этап только в своём `TaskStage::parse` (вернёт `None` и
ошибку `UnknownStage` при следующей попытке перехода для таких задач) —
это приемлемо, так как откат ожидается сразу после проблемного релиза,
пока задач на новом этапе накопилось мало.
