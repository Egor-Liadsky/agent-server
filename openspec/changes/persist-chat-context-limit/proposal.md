## Why

`limit-context-window` (ещё не заархивировано) добавило клиентское поле
`settings.max_context_tokens`, но намеренно ограничило его действие одним
вызовом `POST /v1/chat`: значение не сохраняется в хранилище чата. Решение
было осознанным на тот момент, но теперь клиент (`agent-cli`,
`scope-context-limit-to-chat`) переносит лимит контекста в `ChatSettings` —
делает его настройкой конкретного чата, как модель или стратегию
рассуждения. Без сохранения на стороне `agentd` это остаётся иллюзией:
значение, заданное в клиентском TUI, терялось бы при следующей загрузке
чата. Нужно, чтобы `PATCH /v1/chats/{id}` сохранял `max_context_tokens`
вместе с остальными настройками чата, а `POST /v1/chat` применял сохранённое
значение по умолчанию, продолжая при этом принимать разовое переопределение
на один вызов — как уже работает для `model`, `reasoning`, параметров
сэмплирования.

## What Changes

- `ChatSettingsDto.max_context_tokens` (`src/dto.rs`) переходит на тот же
  двойной `Option` (`double_option`), что уже применяют поля сэмплирования:
  различает «поле не задано» (оставить прежнее значение чата), `null`
  (снять лимит) и число (задать лимит). Раньше поле было одинарным
  `Option<u32>` и означало только «задано на этот вызов».
- `ChatSettingsDto::apply_to` переносит `max_context_tokens` в
  `ChatSettings` наравне с прочими полями — при `PATCH /v1/chats/{id}`
  значение сохраняется в хранилище чата (JSON-колонка `settings`,
  миграция БД не нужна — та же колонка, что уже хранит `model`, `sampling`
  и остальные поля общего типа `agentcore::ChatSettings`).
- `POST /v1/chat` (с `chat_id` и без) продолжает читать
  `settings.max_context_tokens` из тела запроса как разовое
  переопределение эффективного лимита для этого вызова — но теперь поверх
  сохранённого лимита чата, а не поверх «ничего»: `effective_context_limit`
  сравнивает операторский лимит по умолчанию с результатом слияния
  (сохранённый лимит чата, переопределённый разовым значением запроса, если
  оно задано), а не только с разовым значением запроса.
- **BREAKING** (относительно ещё не заархивированного `limit-context-window`):
  `max_context_tokens`, переданный в `PATCH /v1/chats/{id}`, теперь
  сохраняется — раньше сервис такое поле в `PATCH` не читал вовсе (DTO
  не подключал его к `apply_to` для этого пути так, как остальные поля).

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `context-limit` (введена `limit-context-window`, изменение ещё не
  заархивировано — прежняя спека правится напрямую как черновик, а не через
  delta к заархивированной версии): требование «Клиентское сужение лимита
  на один запрос» переформулируется — значение из `PATCH` теперь
  персистентно, значение из `POST /v1/chat` остаётся разовым
  переопределением поверх сохранённого.

## Impact

- Код: `src/dto.rs` (`ChatSettingsDto.max_context_tokens` →
  `double_option`, `ChatSettingsDto::apply_to`), `src/app.rs`
  (`effective_context_limit` — источник клиентского значения меняется с
  «поле запроса как есть» на «настройки чата после слияния с DTO запроса»;
  `server_defaults` — без изменений, у нового чата без клиента лимита нет),
  `src/tests.rs`.
- Хранилище: без миграции — `ChatSettings` хранится одной JSON-колонкой
  (`src/store.rs`, `parse_settings` уже переживает несовместимые/новые поля
  умолчаниями).
- README: раздел про `POST /v1/chat` и `PATCH /v1/chats/{id}` — новое
  поведение `max_context_tokens` при обновлении настроек чата.
- Другой репозиторий: клиентское изменение `agent-cli`,
  `scope-context-limit-to-chat` — переносит поле в `ChatSettings` клиента
  и начинает слать его в `PATCH /v1/chats/{id}`. Порядок раскатки — см.
  `agent-cli/openspec/changes/scope-context-limit-to-chat/design.md`,
  Migration Plan: снять `[patch]` в `.cargo/config.toml`,
  `cargo generate-lockfile`, чтобы подтянуть обновлённый `agentcore` из
  `main` `agent-cli`, `cargo test --locked`.
