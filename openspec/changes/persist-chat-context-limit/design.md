## Context

См. `proposal.md` — Why. `ChatSettings` (`agentcore`, общий тип с
`agent-cli`) хранится в SQLite одной JSON-колонкой `settings`
(`src/store.rs`, `parse_settings`/`store::create_chat`/`store::update_chat`);
несовместимое изменение формы `ChatSettings` не делает чат недоступным —
`parse_settings` при ошибке разбора подставляет умолчания сервиса и
пишет `WARN`. Это уже рассчитано на добавление новых полей ядра без
миграции: `max_context_tokens` в `ChatSettings` (клиентское изменение
`agent-cli`, `scope-context-limit-to-chat`) достаточно передать через
`#[serde(default)]`, и старые строки БД без этого поля читаются как `None`.

`ChatSettingsDto::apply_to` (`src/dto.rs`) — единая точка слияния входящего
DTO с базовыми настройками (`base`), общая для `POST /v1/chat` (`base` —
`server_defaults()` без `chat_id`, либо `chat.settings.clone()` с
`chat_id`) и `PATCH /v1/chats/{id}` (`base` — `chat.settings.clone()`).
Различие в том, сохраняет ли `merge_settings` результат
(`SettingsPurpose::Storage` для `PATCH`, `SettingsPurpose::Call` для
`POST /v1/chat` — вызывающая сторона решает, персистить или нет, сама
`apply_to` этого не знает).

## Goals / Non-Goals

**Goals:**
- `max_context_tokens` ведёт себя как остальные поля `ChatSettingsDto`:
  `PATCH` сохраняет, `POST /v1/chat` может переопределить разово поверх
  сохранённого, не сохраняя переопределение.
- `effective_context_limit` (`src/app.rs`) берёт клиентское значение из
  результата слияния (`ChatSettings.max_context_tokens` после `apply_to`),
  а не из сырого DTO запроса, как раньше.
- Не менять контракт `context_limit_invalid`/`context_limit_exceeded`:
  коды и структура ошибки прежние.

**Non-Goals:**
- Миграция БД — не нужна (см. Context).
- Валидация значения при `PATCH` относительно операторского лимита — как и
  сейчас для прочих полей `ChatSettingsDto`, сервис не проверяет значения
  настроек чата при сохранении против операторских ограничений, кроме уже
  существующих (`validate_settings_for_storage` — белый список моделей,
  Ollama). Превышение операторского лимита обнаруживается в момент вызова
  (`POST /v1/chat`), не при `PATCH`: чат с лимитом больше операторского
  сохранить можно, но любой звонок с ним получит `400
  context_limit_invalid`, пока лимит не понизят или не поднимут
  операторский — тот же принцип, что уже действует для модели вне белого
  списка (`validate_settings_for_storage` пропускает провайдер Ollama
  именно по этой причине; для облачной модели проверка есть — здесь она
  умышленно отсутствует, потому что эффективный лимит зависит и от
  разового значения запроса, а не только от сохранённого).

## Decisions

- **`max_context_tokens` в DTO — `double_option`, как поля сэмплирования.**
  Разграничивает «не трогать», `null` («снять») и число («задать») —
  без этого поле не могло бы участвовать в `PATCH` наравне с `model`.
  Прямая замена одинарного `Option<u32>`, который сейчас (до этого
  изменения) означает только «разовое значение на этот вызов».
- **`effective_context_limit` берёт клиентское значение после `apply_to`, а
  не до.** Раньше `client_context_limit = request.settings.as_ref()
  .and_then(|s| s.max_context_tokens)` вычислялся из сырого DTO запроса до
  вызова `merge_settings`. Теперь источник — `settings.max_context_tokens`
  из уже слитого `ChatSettings` (переменная `settings`, которую
  `handle_ask`/`handle_ask_in_chat` и так строят для `model`). Одна точка
  слияния вместо двух разных путей чтения одного и того же поля.
- **`server_defaults()` не меняется.** Разовый запрос без `chat_id` не
  привязан ни к какому сохранённому чату — лимит контекста для него может
  прийти только через `settings.max_context_tokens` самого запроса, ровно
  как и раньше.
- **Ограничение белым списком моделей при `PATCH` на `max_context_tokens`
  не распространяется.** `validate_settings_for_storage`/
  `validate_settings_for_call` проверяют то, что сервис обязан проверить
  сам перед вызовом провайдера (модель, доступность Ollama); операторский
  лимит контекста — не про допустимость вызова, а про его стоимость, и
  сравнение с ним уже устроено как проверка эффективного лимита в момент
  вызова, а не как поле, которое можно провалидировать в отрыве от
  остальных настроек чата в момент `PATCH`.

## Risks / Trade-offs

- Чат может сохранить `max_context_tokens` больше операторского лимита
  (`PATCH` его не проверяет) — тогда каждый `POST /v1/chat` для этого чата
  получает `400 context_limit_invalid`, пока пользователь не понизит
  сохранённое значение. Смягчение: ответ называет причину и сравниваемые
  числа (`"max_context_tokens не может превышать операторский лимит
  {default}"`), а клиент (`agent-cli`) показывает эту ошибку как обычную
  ошибку запроса — пользователь видит, что чинить нужно настройки чата, а
  не единичный вызов.
- Клиент (`scope-context-limit-to-chat`) может начать слать
  `max_context_tokens` в `PATCH` раньше, чем этот change будет применён:
  сейчас `ChatSettingsDto.max_context_tokens` — одинарный `Option<u32>`,
  который `apply_to` не читает вовсе при `PATCH` (поле объявлено в DTO, но
  не участвует в слиянии для этого пути) — значение молча игнорируется, а
  не приводит к ошибке. Безопасно для независимой раскатки: см.
  `agent-cli/openspec/changes/scope-context-limit-to-chat/design.md`,
  Migration Plan.
