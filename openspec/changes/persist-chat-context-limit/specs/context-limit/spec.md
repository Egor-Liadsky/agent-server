## Purpose

Ограничивает размер истории, отправляемой в вызов модели, операторским
лимитом контекстного окна по умолчанию, который можно сузить постоянно для
конкретного чата или разово для одного запроса, и отклоняет запрос до
обращения к провайдеру, если оценка размера истории эффективный лимит
превышает.

## ADDED Requirements

### Requirement: Операторский лимит контекстного окна по умолчанию

Сервис SHALL читать необязательную переменную окружения
`AGENTD_MAX_CONTEXT_TOKENS` при старте. Заданное значение MUST быть целым
положительным числом токенов; при иначе оформленном значении старт SHALL
завершаться фатальной ошибкой, как для прочих переменных `AGENTD_*` с
числовым значением. Не заданная переменная SHALL означать отсутствие
лимита: проверка размера истории не выполняется, поведение сервиса не
меняется.

#### Scenario: Лимит не задан

- **WHEN** `AGENTD_MAX_CONTEXT_TOKENS` не задана и ни чат, ни запрос не
  задают `max_context_tokens`
- **THEN** сервис отправляет историю модели без проверки её размера

#### Scenario: Некорректное значение лимита при старте

- **WHEN** `AGENTD_MAX_CONTEXT_TOKENS` задана значением, не являющимся
  положительным целым числом
- **THEN** сервис завершается фатальной ошибкой при старте и не начинает
  принимать запросы

### Requirement: Лимит контекста сохраняется в настройках чата

`PATCH /v1/chats/{id}` SHALL принимать в `settings` необязательное поле
`max_context_tokens` — целое положительное число токенов — и сохранять его
в постоянных настройках чата наравне с `model`, `reasoning` и параметрами
сэмплирования. Отсутствие поля в теле запроса SHALL оставлять сохранённое
значение чата без изменений. Явный `null` SHALL снимать сохранённый лимит
чата. Сохранённое значение SHALL действовать как значение по умолчанию для
каждого последующего `POST /v1/chat` этого чата, пока запрос не
переопределит его разово (см. Requirement «Разовое переопределение лимита
на один запрос»).

#### Scenario: Лимит чата сохраняется при обновлении настроек

- **WHEN** `PATCH /v1/chats/{id}` передаёт `settings.max_context_tokens`
  равным N
- **THEN** сервис сохраняет N в настройках чата, и последующий
  `GET /v1/chats/{id}` возвращает `max_context_tokens: N` в составе
  настроек

#### Scenario: Явный null снимает сохранённый лимит

- **WHEN** у чата ранее сохранён `max_context_tokens`, и `PATCH
  /v1/chats/{id}` передаёт `settings.max_context_tokens: null`
- **THEN** сервис снимает сохранённое значение — чат больше не сужает
  операторский лимит по умолчанию, пока не будет задан новый

#### Scenario: Отсутствие поля не трогает сохранённое значение

- **WHEN** у чата ранее сохранён `max_context_tokens`, и `PATCH
  /v1/chats/{id}` обновляет другие поля настроек, не упоминая
  `max_context_tokens`
- **THEN** сохранённый лимит контекста чата остаётся прежним

### Requirement: Разовое переопределение лимита на один запрос

`POST /v1/chat` SHALL принимать в `settings` необязательное поле
`max_context_tokens`, действующее только на этот вызов и не изменяющее
сохранённые настройки чата (даже когда запрос ссылается на `chat_id`).
Заданное значение SHALL заменять сохранённый лимит чата (если он есть) для
расчёта эффективного лимита этого запроса. Итоговое клиентское значение
(разовое, если задано, иначе сохранённое значение чата, иначе не задано),
превышающее операторский лимит по умолчанию (или заданное при отсутствующем
операторском лимите), SHALL быть отклонено ответом `400` с кодом ошибки
`context_limit_invalid`, а вызов модели SHALL не выполняться.

#### Scenario: Разовое значение уже, чем сохранённый лимит чата

- **WHEN** у чата сохранён `max_context_tokens = 8000`, а запрос передаёт
  `settings.max_context_tokens = 4000`, не превышающее операторский лимит
- **THEN** сервис использует `4000` как эффективный лимит для этого
  запроса, а сохранённый лимит чата остаётся `8000`

#### Scenario: Запрос без своего значения использует лимит чата

- **WHEN** у чата сохранён `max_context_tokens = 4000`, а запрос
  `settings.max_context_tokens` не передаёт
- **THEN** сервис использует сохранённый лимит чата (`4000`) как
  эффективный лимит для этого запроса

#### Scenario: Итоговое значение превышает операторский лимит

- **WHEN** операторский лимит по умолчанию задан значением N, и итоговое
  клиентское значение (разовое или сохранённое) больше N, либо операторский
  лимит не задан, а клиентское значение задано
- **THEN** сервис отклоняет запрос `400` с кодом `context_limit_invalid` и
  не обращается к провайдеру

### Requirement: Отказ при превышении эффективного лимита

Перед вызовом конвейера обработки сервис SHALL оценить размер истории,
которая будет передана модели (объединение уже сохранённых сообщений чата,
если запрос ссылается на `chat_id`, и присланных клиентом `prompt` или
`messages`), в токенах. Оценка размера MAY быть приближённой при
отсутствии точного токенизатора провайдера, но SHALL быть документирована
как оценка. Если оценка превышает эффективный лимит (см. Requirement
«Разовое переопределение лимита на один запрос»), сервис SHALL отклонить
запрос ответом `400` с кодом ошибки `context_limit_exceeded` и SHALL не
обращаться к провайдеру. Запрос, для которого эффективный лимит не
определён (лимит по умолчанию не задан, и ни чат, ни запрос своего
значения не задают), SHALL не подчиняться этой проверке.

#### Scenario: История превышает эффективный лимит

- **WHEN** оценка размера истории и нового сообщения в токенах превышает
  эффективный лимит запроса
- **THEN** сервис отвечает `400` с кодом `context_limit_exceeded`, не
  вызывая провайдера, и запрос с `chat_id` не дописывает историю чата

#### Scenario: История укладывается в эффективный лимит

- **WHEN** оценка размера истории и нового сообщения в токенах не
  превышает эффективный лимит запроса
- **THEN** сервис вызывает провайдера как обычно
