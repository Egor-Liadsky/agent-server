## Context

См. `proposal.md` — Why. Проверка нужна до сериализации истории в вызов
провайдера: место — обработчики `/v1/chat` в `src/app.rs`, до
`RequestContext::new` (строки 307 и 354), где для обоих путей (с `chat_id`
и без) уже собрана полная история как `Vec<Message>`. Точного токенизатора
провайдера (`deepseek-chat` через `agentupstream`, либо Ollama) в
зависимостях нет и добавлять его не требуется — оценка приближённая.

## Goals / Non-Goals

**Goals:**
- Единая точка проверки эффективного лимита для обоих обработчиков
  `/v1/chat` (разовый вызов и вызов с `chat_id`), без дублирования логики.
- Эффективный лимит вычисляется без похода в базу сверх той истории, что
  обработчик уже читает для вызова конвейера.

**Non-Goals:**
- Точный подсчёт токенов конкретного провайдера — оценка по длине текста
  достаточна, инвазивная интеграция с чужим токенизатором не входит в
  изменение.
- Изменение поведения `agentcore`/`Pipeline` — лимит проверяется целиком в
  `agentd`, до вызова `Pipeline::run`.
- Настройка лимита на стороне `agentcli` (клиента) — предмет отдельного
  изменения в `agent-cli`, см. `proposal.md` — Impact.

## Decisions

- **Оценка размера — по длине текста, не по внешнему токенизатору.**
  Простая эвристика `ceil(количество символов / 4)` по объединённому тексту
  роли и содержимого каждого сообщения истории плюс нового сообщения.
  Рассмотренная альтернатива — тянуть `tiktoken`-совместимую библиотеку:
  отклонено, так как она считает токены конкретной модели OpenAI, а сервис
  работает и с DeepSeek, и с Ollama, для которых точных таблиц токенизации
  нет; несовпадение с реальным токенизатором провайдера всё равно осталось
  бы. Эвристика оформляется как заведомая оценка (см. spec, Requirement
  «Отказ при превышении эффективного лимита»), а не как точный подсчёт.
- **Эффективный лимит — не таблица лимитов по имени модели.** Один
  операторский лимит `AGENTD_MAX_CONTEXT_TOKENS`, а не сопоставление
  `allowed_models` → лимит: развёрнутый экземпляр `agentd` обычно смотрит
  в одного провайдера с известным оператору окном, вести таблицу под все
  возможные модели избыточно. Если понадобится разный лимit для разных
  `allowed_models`, это отдельное расширение конфигурации.
- **Проверка — до вызова конвейера, а не внутри `Pipeline`.** Лимит — это
  ограничение транспортного уровня (тело `/v1/chat`, а не поведение модели
  или политика конвейера), и `agentcore` не должен знать о HTTP-контракте
  `agentd`. Проверка живёт в `src/app.rs`, рядом со сборкой
  `RequestContext`.
- **Клиентское поле только сужает.** Разрешить клиенту увеличивать лимит
  выше операторского свело бы лимит к декоративному — сервис обязан
  оставаться источником истины о допустимом размере контекста; отсюда
  `400 context_limit_invalid` на попытку увеличить.

## Risks / Trade-offs

- Эвристика по символам может как переоценить, так и недооценить реальное
  число токенов провайдера → отклонённый запрос, который провайдер принял
  бы, или наоборот. Митигация: эвристика документирована в README и в
  сообщении ошибки как оценка; оператор подбирает
  `AGENTD_MAX_CONTEXT_TOKENS` с запасом относительно реального окна модели.
- Операторский лимит общий для всех `allowed_models` → при разнородных по
  размеру окна моделях лимит придётся ставить по самой маленькой. Принято
  как компромисс (см. Decisions); отдельное расширение — предмет будущего
  изменения при реальной необходимости.
