## Why

Сервис `agentd` пересылает провайдеру всю историю `messages`/`prompt` без
проверки её размера: клиент может собрать переписку, которая упрётся в
лимит контекстного окна модели уже на стороне провайдера — с непрозрачной
ошибкой апстрима вместо понятного ответа сервиса. Лимит должен проверяться
на сервере (владельце вызова модели и ключа провайдера), а не в клиенте,
но клиент должен иметь возможность настроить своё, более узкое значение.

## What Changes

- Появляется настраиваемый оператором лимит контекстного окна по умолчанию:
  `AGENTD_MAX_CONTEXT_TOKENS` — целое число токенов, соответствующее
  реальному окну развёрнутой модели. Не задан — лимит не проверяется
  (текущее поведение сохраняется).
- `ChatSettingsDto` (`POST /v1/chat`, поле `settings`) пополняется
  необязательным полем `max_context_tokens`. Клиент может этим полем
  только сузить эффективный лимит для одного запроса — значение, большее
  операторского умолчания, отклоняется `400` (`context_limit_invalid`).
  Без поля действует операторское умолчание.
- Перед вызовом модели сервис оценивает размер истории (`history` +
  `prompt`/`messages`) в токенах и, если оценка превышает эффективный
  лимит, отклоняет запрос `400` с кодом `context_limit_exceeded` без
  обращения к провайдеру. Запрос без операторского умолчания и без
  клиентского поля лимиту не подчиняется.
- Точного токенизатора провайдера у сервиса нет: размер оценивается
  приближённо (по длине текста) и документируется как оценка, а не точный
  подсчёт токенов провайдера.
- Настройка `max_context_tokens`, как и остальные поля `settings` на разовый
  запрос, в базу чата не пишется (согласуется с уже принятым поведением
  `POST /v1/chat` из `add-chat-storage-sqlite`).

## Capabilities

### New Capabilities

- `context-limit`: операторский лимит контекстного окна по умолчанию,
  клиентское поле, которое может лишь сужать его на один запрос, оценка
  размера истории в токенах и отказ `400` до вызова модели при превышении.

### Modified Capabilities

Нет: `openspec/specs/` пуст, контракт `/v1/chat` спецификацией пока не
описан (описывается впервые вместе с этим изменением — `context-limit`
задаёт только новые требования, не переопределяет существующие).

## Impact

- Код: `src/config.rs` (`AGENTD_MAX_CONTEXT_TOKENS`), `src/dto.rs`
  (`max_context_tokens` в `ChatSettingsDto`), `src/app.rs` (проверка лимита
  перед вызовом конвейера в обоих обработчиках `/v1/chat`), `src/error.rs`
  (коды `context_limit_invalid`, `context_limit_exceeded`), `src/tests.rs`
  (лимит по умолчанию, сужение клиентом, превышение, попытка увеличить).
- Ядро `agentcore` не трогается: оценка размера и отказ — целиком в
  `agentd`, до передачи истории в `Pipeline`.
- Эксплуатация: README (переменная `AGENTD_MAX_CONTEXT_TOKENS`, поле
  `max_context_tokens`, новые коды ошибок).
- Смежный репозиторий: чтобы клиент мог настраивать `max_context_tokens`,
  `agentcli` должен научиться передавать это поле в `ChatSettings` и
  пробрасывать его в тело `POST /v1/chat` — отдельное изменение в
  `agent-cli`, здесь описывается только контракт сервиса, который клиент
  сможет использовать.
