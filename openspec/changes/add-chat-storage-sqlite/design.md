## Context

Мотивация — в `proposal.md`, требования — в `specs/chat-storage/spec.md` и
`specs/chat-api/spec.md`. Здесь только то, что определяет реализацию.

Сегодня сервис не имеет состояния: `AppState` держит конфигурацию и один
клиент провайдера, обработчик `chat` собирает историю из тела запроса и
отдаёт её конвейеру `agentcore::pipeline`. Хранилища нет ни в каком виде,
поэтому изменение вводит новый слой целиком, а не переделывает существующий.

Ограничения, которые формируют решение:

- ядро `agentcore` о базе знать не должно, зависимость на SQLite живёт только
  в сервисе;
- конфигурация — только переменные окружения `AGENTD_*`;
- сервис работает в контейнере одним процессом, база — локальный файл;
- одновременных запросов немного (`AGENTD_MAX_CONCURRENCY`, по умолчанию 16),
  и почти все они упираются в ожидание провайдера, а не в базу.

## Goals / Non-Goals

**Goals:**

- слой хранилища с узким интерфейсом, за которым скрыт конкретный драйвер:
  обработчики оперируют чатами и сообщениями, а не SQL;
- схема, которую можно перенести на серверную СУБД без смены контракта `/v1`;
- предсказуемое поведение при конкурентной записи и при отказе провайдера;
- обратная совместимость: существующий клиент, не знающий о чатах, работает
  без изменений.

**Non-Goals:**

- абстракция «любая СУБД» с несколькими реализациями трейта хранилища:
  вторая СУБД не нужна, а её ожидание усложняет код без пользы;
- кеш чатов в памяти: узкое место — провайдер, а не чтение локального файла;
- фоновая обрезка истории, ретеншен, экспорт — вне области изменения.

## Decisions

### Решение 1. Доступ к SQLite: `sqlx` с драйвером `sqlite`

Выбран `sqlx` (`features = ["runtime-tokio", "sqlite", "migrate"]`) вместо
`rusqlite` за `spawn_blocking`.

Почему:

- у `sqlx` уже есть асинхронный интерфейс, пул (`SqlitePool`) и исполнитель
  миграций (`sqlx::migrate!`) — то есть три куска инфраструктуры, которые с
  `rusqlite` пришлось бы писать и тестировать самим (`r2d2` или свой пул,
  свой раннер миграций с таблицей версий, обёртки `spawn_blocking` вокруг
  каждого запроса);
- `sqlx-sqlite` сам исполняет запросы на выделенном потоке соединения,
  поэтому блокирующий вызов не встаёт в исполнитель tokio — ровно то, ради
  чего в варианте с `rusqlite` понадобился бы `spawn_blocking`;
- `libsqlite3-sys` собирается в режиме `bundled`, поэтому рантайм-образ
  остаётся без системного SQLite, а `Dockerfile` — без новых пакетов
  рантайма.

Цена: заметный рост дерева зависимостей и времени сборки, чего у `rusqlite`
нет. Считаем приемлемым: сборка идёт в многостадийном образе и в CI, а
самописный пул с раннером миграций дороже в поддержке, чем минуты сборки.

Отдельно: используется только рантайм-API (`sqlx::query`, `query_as`), а не
макросы `query!`. Макросы требуют живой базы или файла `.sqlx` во время
компиляции — это добавило бы `sqlx-cli` в сборку образа и в CI. Проверка
типов запросов теряется, её заменяют тесты хранилища.

Альтернатива `rusqlite` + `spawn_blocking` остаётся запасной: интерфейс
хранилища описан своими типами, а не типами `sqlx`, поэтому замена драйвера
не задевает обработчики.

### Решение 2. Режим базы и параметры соединения

На каждом соединении пула выставляются:

- `journal_mode = WAL` — читатели не блокируют писателя и наоборот; для
  сервиса, где чтение списка идёт одновременно с записью обмена, это
  единственный разумный режим. WAL создаёт рядом с базой файлы `-wal` и
  `-shm`, поэтому том монтируется на каталог, а не на файл;
- `foreign_keys = ON` — в SQLite это признак соединения, а не базы: без него
  каскадное удаление сообщений молча не работает;
- `busy_timeout = AGENTD_DB_BUSY_TIMEOUT_MS` (по умолчанию 5000 мс) —
  ожидание освобождения блокировки записи вместо немедленного
  `SQLITE_BUSY`;
- `synchronous = NORMAL` — при WAL этого достаточно: потеря возможна только
  при отказе питания или ядра ОС, но не при падении процесса, а `FULL`
  заметно дороже на каждой записи.

Пул — `AGENTD_DB_MAX_CONNECTIONS`, по умолчанию 5. Обоснование величины:
писатель в SQLite всё равно один, соединения нужны читателям, а читающие
запросы к локальному файлу измеряются десятками микросекунд. Пять соединений
покрывают дефолтные 16 одновременных запросов с запасом; больше соединений
дало бы только рост числа файловых дескрипторов и конкуренции за блокировку.

Все пишущие транзакции открываются как `BEGIN IMMEDIATE`. Иначе транзакция
начинается как читающая и повышается до пишущей на первой записи, а такое
повышение при занятой базе возвращает `SQLITE_BUSY` немедленно, не дожидаясь
`busy_timeout`.

### Решение 3. Схема

```sql
CREATE TABLE chats (
    id          TEXT    PRIMARY KEY,
    owner       TEXT    NOT NULL,
    title       TEXT    NOT NULL,
    settings    TEXT    NOT NULL,   -- JSON ChatSettings
    created_at  INTEGER NOT NULL,   -- секунды Unix
    updated_at  INTEGER NOT NULL
);
CREATE INDEX chats_owner_updated ON chats (owner, updated_at DESC, id DESC);

CREATE TABLE messages (
    id          TEXT    PRIMARY KEY,
    chat_id     TEXT    NOT NULL REFERENCES chats (id) ON DELETE CASCADE,
    seq         INTEGER NOT NULL,
    role        TEXT    NOT NULL,   -- 'user' | 'assistant'
    content     TEXT    NOT NULL,
    reasoning   TEXT,
    meta        TEXT,               -- JSON MessageMeta
    created_at  INTEGER NOT NULL,
    UNIQUE (chat_id, seq)
);
```

Разобранные развилки:

- **Порядок сообщений — явная колонка `seq`, а не `rowid` и не время.**
  `rowid` — деталь SQLite и на серверной СУБД не переносится; время в
  секундах не различает два сообщения одного обмена. `seq` считается внутри
  той же транзакции (`MAX(seq) + 1` по чату), а `UNIQUE (chat_id, seq)`
  делает нарушение порядка ошибкой записи, а не тихой порчей истории.
  Индекс по `(chat_id, seq)` создаётся ограничением `UNIQUE`, отдельный не
  нужен.
- **Идентификаторы — UUID v4 текстом, а не автоинкремент.** Крейт `uuid` уже
  в зависимостях. Числовой идентификатор раскрывал бы число чатов в сервисе
  и позволял бы перебор чужих; кроме того, генерация на стороне сервиса не
  зависит от СУБД, что важно для будущего переезда.
- **Настройки чата — JSON целиком, а не колонки под каждое поле.**
  `ChatSettings` — структура ядра из соседнего репозитория; раскладка её по
  колонкам означала бы миграцию базы на каждое изменение ядра. Все поля
  `ChatSettings` помечены `#[serde(default)]`, поэтому старые строки читаются
  и после добавления полей. Цена — по настройкам нельзя искать и фильтровать;
  таких запросов в контракте нет.
- **Телеметрия сообщения — JSON `meta`.** См. решение 6.
- **Индекс списка — `(owner, updated_at DESC, id DESC)`.** Совпадает с
  порядком и с ключом постраничной выдачи, поэтому список читается
  просмотром индекса без сортировки.

Схема не использует ничего, чего нет в серверных СУБД: типы, внешний ключ и
уникальность переносятся дословно, а `seq` вместо `rowid` снимает
единственную зависимость от SQLite.

### Решение 4. Миграции

Каталог `migrations/` в корне репозитория, файлы вида
`0001_init.sql`, применяются `sqlx::migrate!()` при старте до начала
прослушивания порта. `sqlx` ведёт таблицу `_sqlx_migrations` с контрольными
суммами: повторный запуск ничего не делает, изменённая ранее применённая
миграция — ошибка старта (см. требование об идемпотентных миграциях).

Каждый файл миграции — одна транзакция, поэтому частично применённой схемы
не остаётся.

`sqlx::migrate!` встраивает содержимое каталога в бинарник во время
компиляции, поэтому рантайм-образу каталог `migrations/` не нужен, а стадии
сборки — нужен: в `Dockerfile` добавляется `COPY migrations ./migrations`.

Порядок старта: разбор конфигурации → создание каталога базы → открытие пула
→ миграции → `AppState` → прослушивание. Любая ошибка на этом пути печатается
с путём к базе и завершает процесс ненулевым кодом, как отсутствующий
`AGENTD_UPSTREAM_API_KEY`.

### Решение 5. Судьба `POST /v1/chat` без `chat_id` — сохранить как есть

Вариант выбран из трёх: сохранить, объявить устаревшим, создавать чат неявно.

- Неявное создание чата отвергнуто: тогда каждый `agentcli ask` оставлял бы
  чат из одного обмена, база росла бы мусором, а клиент не имел бы способа
  отказаться от сохранения.
- Объявление устаревшим отвергнуто: разовый вызов без истории — законный
  сценарий (`ask`, проверка сервиса, интеграции), он не станет ненужным
  после перехода клиента на серверные чаты.
- Сохранение как есть даёт обратную совместимость: клиент, ничего не знающий
  о чатах, продолжает работать, и переход `agentcli` можно делать отдельным
  изменением, не синхронизируя выкладку.

Поля тела при заданном `chat_id`: `prompt` — новое сообщение, `messages` —
`400`, `settings` — переопределение на один запрос. Разделение
«разово — `POST /v1/chat`, насовсем — `PATCH /v1/chats/{id}`» выбрано вместо
«`settings` всегда сохраняется»: иначе однократный эксперимент с
`temperature` тихо менял бы чат навсегда, и вернуть прежнее значение можно
было бы только повторным запросом.

### Решение 6. Что сохраняется в сообщении

Сохраняются роль, текст, `reasoning` и `MessageMeta` целиком; `PolicyLog` не
сохраняется.

`reasoning` и телеметрия сохраняются потому, что сегодня они лежат в
`~/.config/agentcli/chats/*.json` и показываются в TUI. Если сервер их не
сохранит, переход клиента на серверные чаты станет потерей функции, а
восстановить их будет неоткуда. Объём данных мал по сравнению с самим
текстом.

`PolicyLog` — след обработки одного запроса, а не часть переписки: он
относится к стадиям конвейера и уже возвращается в ответе и пишется в
журнал. Хранение его в истории смешало бы диалог с диагностикой.

`MessageMeta` кладётся в JSON-колонку `meta`, а не в отдельные колонки: это
структура ядра, она меняется вместе с ним, а агрегатных запросов по токенам
контракт не требует. Наружу она отдаётся разобранной — полями `usage`,
`timing` и `model`, теми же, что и в ответе `POST /v1/chat`, поэтому клиенту
не нужен второй формат телеметрии.

### Решение 7. Владение чатом

`owner` — `sha256("agentd-client-token:v1:" || токен)` в шестнадцатеричном
виде. Постоянный префикс разделяет области применения хеша, чтобы отпечаток
нельзя было сопоставить с хешем того же токена из другого места. Добавляется
зависимость `sha2`.

Отвергнутые варианты:

- хранить сам токен — прямо запрещено постановкой задачи и делает базу
  источником секретов;
- хранить порядковый номер токена в `AGENTD_CLIENT_TOKENS` — при
  перестановке или удалении элемента списка чужие чаты достались бы другому
  клиенту;
- солёный хеш с солью в базе — соль пришлось бы хранить рядом с
  отпечатками, а при пересоздании базы владение терялось бы; выигрыш только
  против радужных таблиц, которых для случайного токена и так нет.

Ограничение названо прямо: это не хранилище паролей. Токен с малой энтропией
подбирается по отпечатку перебором, поэтому `AGENTD_CLIENT_TOKENS` должны
быть случайными строками достаточной длины.

При пустом `AGENTD_CLIENT_TOKENS` владельцем становится литерал
`anonymous` — не отпечаток, поэтому анонимные чаты никогда не совпадут с
чатами токенизированного клиента.

Чужой чат отвечает `404 chat_not_found` тем же телом, что и несуществующий.
Реализуется это тем, что владелец входит в условие выборки: запрос «чат по
`id` и `owner`» не находит строки в обоих случаях, и отдельной ветки
«нашли, но не ваш» в коде нет — так расхождение ответов не может появиться
случайно.

### Решение 8. Постраничная выдача

- **Список чатов — keyset по `(updated_at DESC, id DESC)`.** Курсор —
  непрозрачная строка: base64url от `updated_at:id`. Смещение (`OFFSET`)
  отвергнуто: список сортируется по времени изменения, поэтому активный чат
  перескакивает на первую страницу и при обходе со смещением записи
  дублируются и теряются. Непрозрачность курсора оставляет свободу сменить
  ключ выдачи, не меняя контракт. `limit` по умолчанию 50, предел 200.
- **Сообщения — `after` по номеру, а не курсор.** Номер сообщения и так
  публичен (`seq` в ответе), монотонен и никогда не меняется, поэтому
  прятать его в непрозрачную строку смысла нет, а клиенту удобно
  дочитывать чат с известного места. `limit` по умолчанию 200, предел 500.

Ассиметрия намеренная: у списка ключ выдачи изменчив, у сообщений — нет.

### Решение 9. Момент записи обмена

Сообщение пользователя и ответ модели пишутся одной транзакцией **после**
успешного ответа модели, а не по мере поступления.

Альтернатива — писать сообщение пользователя до вызова провайдера — даёт
после сбоя чат с висящим вопросом без ответа, и клиенту нужен отдельный
способ такую запись удалить или доотвечать. Выбранный порядок делает
единицей истории обмен: либо в чате появились оба сообщения, либо чат не
изменился и запрос повторяется как есть.

Цена: при падении процесса между ответом провайдера и записью ответ теряется,
хотя за него уже заплачено. Это редкий случай и он предпочтительнее
постоянного риска рассинхронизации.

История для вызова модели — сохранённые сообщения плюс новое сообщение
пользователя, добавленное только в памяти.

### Решение 10. Размещение в коде

Новый модуль `src/store.rs` (при росте — каталог `src/store/`): типы `Chat`,
`ChatMessage`, `NewMessage`, ошибки хранилища и операции
(`create_chat`, `list_chats`, `load_chat`, `load_messages`, `update_chat`,
`delete_chat`, `append_exchange`). Модуль не знает ни про axum, ни про
`ApiError`: отображение ошибок хранилища в HTTP живёт в `src/error.rs`.

`AppState` получает поле `db: SqlitePool`. Обработчики чатов кладутся в
`src/app.rs` рядом с существующими, DTO — в `src/dto.rs`.

Тесты — в `src/tests.rs`, каждый на своей временной базе во временном
каталоге (`tempfile`), удаляемой вместе с ним. База в памяти не годится:
`:memory:` даёт отдельную базу каждому соединению пула. Провайдер
по-прежнему подменяется `wiremock`.

### Решение 11. Путь к базе по умолчанию и том

`AGENTD_DB_PATH` по умолчанию — `agentd.db` в рабочем каталоге. Абсолютный
путь по умолчанию (например, `/var/lib/agentd/agentd.db`) отвергнут: при
`cargo run` он недоступен на запись и требует прав администратора для
первого запуска.

Контейнер задаёт путь явно: `Dockerfile` создаёт `/var/lib/agentd`,
принадлежащий пользователю `agentd`, объявляет `VOLUME /var/lib/agentd` и
`ENV AGENTD_DB_PATH=/var/lib/agentd/agentd.db`. Том — на каталог, потому что
WAL создаёт рядом с базой файлы `-wal` и `-shm`. Без тома база осталась бы в
слое контейнера и исчезала бы вместе с ним.

`agentd.db` и его спутники добавляются в `.gitignore`; `.dockerignore`
менять не нужно — `migrations/` в нём не исключён, а в контекст сборки
попадает явным `COPY`.

## Risks / Trade-offs

- **Один писатель в SQLite.** → Записи короткие (одна транзакция на обмен,
  вне вызова провайдера), WAL не блокирует читателей, `busy_timeout` гасит
  всплески. Если упрёмся — переезд на серверную СУБД, под который схема уже
  подготовлена.
- **Рост дерева зависимостей и времени сборки из-за `sqlx`.** → Собирается
  только драйвер `sqlite` без макросов и без TLS-функций; интерфейс
  хранилища описан своими типами, поэтому замена на `rusqlite` остаётся
  возможной без правки обработчиков.
- **Файл базы содержит переписку в открытом виде.** → Проговорено в
  требованиях; шифрование и ретеншен вне области. Каталог принадлежит
  пользователю `agentd`, права — только владельцу.
- **Отпечаток токена перебирается при слабом токене.** → Требование к
  `AGENTD_CLIENT_TOKENS` быть случайными строками фиксируется в README.
- **Несовместимое изменение `ChatSettings` в ядре сделает сохранённый JSON
  неразбираемым.** → Поля ядра помечены `#[serde(default)]`, поэтому опасно
  только переименование варианта перечисления. При неудачном разборе
  настроек чата берутся умолчания сервиса и пишется `WARN` с идентификатором
  чата: чат остаётся рабочим, а расхождение видно в журнале. Отказ отвечать
  на такой чат был бы хуже — он делал бы переписку недоступной из-за правки
  в соседнем репозитории.
- **Потеря ответа при падении процесса между ответом провайдера и записью.**
  → Принято сознательно, см. решение 9.
- **Файл базы под `cargo run` появляется в рабочем каталоге.** → Добавляется
  в `.gitignore`; в контейнере путь задан явно.

## Migration Plan

Данные не переносятся: у сервиса состояния не было, база создаётся пустой при
первом старте. Локальные чаты `agentcli` остаются у клиента и импортируются
(или нет) отдельным изменением в `agent-cli`.

Выкладка: новая версия стартует, применяет миграции на пустой или уже
мигрированной базе и продолжает обслуживать прежние запросы `POST /v1/chat`
без `chat_id` без изменений.

Откат: вернуть предыдущий образ. Прежняя версия базы не касается — файл
остаётся лежать и подхватывается при возврате новой версии. Обратные
миграции не пишутся: единственная миграция создаёт схему с нуля, а откат
данных означал бы удаление переписки.

Порядок работ по репозиториям: изменение целиком внутри `agent-sever`, ядро
не трогается. Если правка ядра всё же понадобится, она идёт отдельным
изменением в `agent-cli`, пушится в `main`, и только затем `Cargo.lock`
сервиса обновляется на новый коммит.
